01

A platform-wide silent drop after an event-contract change

Data integrity · event-sourced pipeline

  • PostgreSQL
  • SQL
  • Row-level security
  • Event contracts
  1. 1

    Problem

    After a backend upgrade of an event contract (V6 to V9), every newly created record vanished from customer reports, while internal admin views looked fine. Nothing errored.

  2. 2

    Root cause

    Reports filtered rows through row-level security keyed on a field that the new event version populated differently, so new records matched no tenant rule and were dropped silently.

  3. 3

    Solution

    A backward-compatible key fix (COALESCE across old and new fields), validated in SQL before release against the full history.

  4. 4

    Result

    Zero key changes across 5.28M historical rows; new records visible again for all customers.

  1. Publisher (V9 event)
  2. Queue
  3. Data lake
  4. RLS key mismatch
  5. Report

02

Hidden loads and duplicate scans, traced upstream

Data quality · reconciliation · ingestion

  • PostgreSQL
  • AWS Lambda
  • Reconciliation
  • Python
  1. 1

    Problem

    Two symptoms: roughly 10,080 receiving loads across about 30 accounts were missing from a customer-facing report for two months, and a data model had weak relationships because of duplicated records.

  2. 2

    Root cause

    A delete-cascade defect left dimension references unresolved, so security filters dropped the fact rows. Separately, 43,700 duplicate groups across 65 tenants came from ingestion functions doing a non-atomic check-then-insert.

  3. 3

    Solution

    A tenant-safe fallback in the query layer for the hidden loads, reconciled exactly against the data lake. For the duplicates, I traced them to the ingestion code rather than masking them downstream.

  4. 4

    Result

    ~10,080 loads recovered and matched exactly to the lake; the duplicates were quantified and traced to their source.

  1. Ingestion (check, then insert)
  2. Race: duplicate rows
  3. Fact table
  4. Relationships go many-to-many
  5. Wrong report values

03

Payroll reports blank for ~530 tenants

Root-cause analysis · materialized views

  • PostgreSQL
  • Materialized views
  • Window functions
  1. 1

    Problem

    A customer-facing payroll metric went blank across the platform after an event-schema change.

  2. 2

    Root cause

    A window function partitioned by a key that became NULL, inside a five-layer chain of materialized views.

  3. 3

    Solution

    A one-line fix, validated read-only end to end, plus an assessment of the five dependent views before proposing it.

  4. 4

    Result

    0 to 51,265 records correctly assigned in validation; about 530 tenants affected.

  1. Event schema change
  2. NULL partition key
  3. MV layers 1 to 5
  4. Metric

04

Faster analytics on Aurora: 9.9 s to 80 ms

Performance · autovacuum · materialized views

  • PostgreSQL / Aurora
  • SQL
  • Migrations
  • AWS CDK
  1. 1

    Problem

    Slow, failing refreshes for reporting workloads, including disk-full errors from a compute-heavy calculation in the refresh path.

  2. 2

    Root cause

    Autovacuum lag and a dirty visibility map on a 6M-row table slowed a critical query; a heavy revenue calculation spilled temp files.

  3. 3

    Solution

    Per-table autovacuum tuning via a migration, index-aware SQL guided by EXPLAIN (ANALYZE, BUFFERS), and the revenue calculation moved into a scheduled materialized view.

  4. 4

    Result

    Critical query ~9.9 s to ~80 ms; an extraction from 73 s to 20 s; materialized-view refresh from 15+ min to 40 s, and data lag from 7 days to 1 day.

Also shipped: Python/SAM to TypeScript/CDK migration

Led the migration of three production Lambdas that deliver scheduled reports to 50+ customer channels: byte-identical output, a 223-test suite with mutation testing, a controlled cutover through the deployment pipeline, and resolution of seven post-release issues. Along the way I fixed a duplicate-run incident traced in CloudWatch to a timeout plus async retry, and cut per-tenant query time from over 3 minutes to under 1 second.

02

Power BI and semantic modeling

可視化

My secondary skill. I treat reports as the last layer of a pipeline: models, refresh strategy and security rules are engineered and validated against the source, not eyeballed.

Measures that lied

Audited a customer-facing model and fixed measures with mismatched denominators that overstated defect rates by ~9.5 percentage points, a fan-out that inflated another rate by ~5 points, and a measure that under-reported by 42%. Every on-screen number was validated against PostgreSQL.

Stale numbers after a price load

Diagnosed a non-uniform +2% to +38% mismatch as incremental-refresh partitions that were never reprocessed (93.7% of one customer's scans fell outside the refresh window), proved it by replaying the calculation with old prices, and defined a targeted partition-reprocess step.

Business logic moved into SQL

Led the move of logic from embedded Power Query/native SQL into 35 PostgreSQL reporting views packaged as migrations with rollback, and wrote Python tooling that parses PBIP/TMDL to inventory model partitions.

Scoping a migration with code

Parsed report and model definitions with Python to cut 146 measures down to the 47 in use on visible pages, which scoped a move to an in-house analytics platform.

Capacity and refresh reliability

Diagnosed Fabric capacity alerts as interactive bursts on top of unchanged background refresh and cut refresh windows from 5 years to 1 across 17 tables, bringing utilisation to ~50%. Restored stalled refreshes by isolating an expired credential and wrote a triage runbook.

Row-level security done right

Fixed quality visuals that had failed under RLS for ~3 months by identifying an ambiguous many-to-many path and deactivating it after auditing 11 reports. Debugged embed issues by instrumenting the real embedded session.

Earlier roles: Fabric lakehouse with medallion layers and schema-drift checks; Power BI semantic models and DAX for executive KPIs; a finance request app on Power Apps, Dataverse and Power BI across DEV/UAT/PROD.
